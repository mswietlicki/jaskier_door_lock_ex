Four-Door 12 V Actuator Lock Controller

One ESP32-S3-DevKitC-1 running ESPHome drives four fully independent door locks from one board: four DRV8871 H-bridges, four INA219 high-side current monitors on a shared I²C bus, one MH-MINI-360 buck, one 4S LiFePO4 pack. Per door, the circuit and the firmware are identical to variant A — end of travel and obstructions are both read out of the motor current, no extra sensors.

This document covers variant B (door_lock_b.yaml). The single-door build is documented in wiring.html; everything said there about the current path, star grounds and threshold tuning applies here to each of the four branches.

Set the buck output first

The MH-MINI-360 ships with its trimpot in an arbitrary position and will happily pass something close to 12 V straight through. The DevKitC-1's 5V pin feeds its on-board regulator and USB rail — anything well above 5 V destroys it.

Wire U4 to the pack with nothing on its output, measure OUT+ to OUT− with a meter, turn the trimpot until it reads 5.00 V, then power down and connect U1.

Two things a door lock has to get right — times four

Every one of the four doors keeps a mechanical override — a key cylinder or a thumb turn — that works with the electronics dead. And no actuator may trap anyone inside; each bolt must be releasable from the protected side without power.

Two design consequences worth flagging up front. First, the firmware drives every bridge fully on, never PWM — PWM would chop the current the INA219s see and make stall detection unreliable. Second, the doors are fully independent and can all move at once: four actuators stalling together draw around 2 A plus inrush, which is why F1 is 5 A here rather than variant A's 2 A, and why every 12 V run is sized for the sum, not one motor.

Never bridge a shunt — now four chances to get it wrong

Every INA219 brings VIN+ and VIN− out twice — as large pads for load current and again on the 6-way header. Each pair is the same copper, with a single 0.1 Ω shunt between them. Wire the big pair only and leave the header pins empty, on all four modules.

Land two wires from the same side of the circuit on both footprints and you short across that shunt. The motor still runs normally, so nothing looks broken — but that door's current reads ≈ 0 A forever, every move ends instantly as "current collapsed", and its jam detection never fires. Before wiring each module, check with a meter: VIN+ to VIN− about 0.1 Ω, big-to-small on the same name about 0 Ω.

How a move ends Figure B3

Every move is a race between four outcomes. The firmware samples the INA219 at 20 Hz, ignores the first 400 ms of inrush, then needs three consecutive samples past a threshold before it commits — one noisy reading never triggers anything.

Perfboard layout

The schematic is drawn as a fused +12 V spine with four identical branches because that is how it should be built: a bare 16 AWG +12 V rail along one edge, a bare 16 AWG GND rail along the other, the ESP in the middle, and the four shunt-bridge pairs in a row between them. Beyond variant A's rules (all of which still apply):

  • Keep each door's branch together. U3n → U2n → motor terminals should sit next to each other, one column per door. Never route one door's motor pair past another door's INA219.
  • C1 and C2 at every bridge's power terminals — four sets, not one shared set at the battery. Four motors switching on the same rail is exactly the brown-out scenario they exist for.
  • Star the grounds — ten returns. BAT1 − is the star: four bridge motor returns, four INA219 references, U4, and U1 each land on the rail with their own wire. A shared return between a bridge and an INA219 corrupts that door's current reading; a shared return between two bridges couples the doors' noise.
  • One I²C bus, kept short. Chain SDA/SCL along the four modules on the side of the board away from the motor wiring, whole run under ~25 cm. Four modules put four 10 k pull-ups in parallel (≈ 2.5 k effective) — that is comfortably strong at 400 kHz; do not add the extra 4.7 k resistors from the variant A notes.
  • Screw terminals for everything leaving the board — pack and all four motors. Ten flying leads soldered to perfboard will not survive four slamming doors.
  • Fuse for the sum. F1 is 5 A because all four doors may legitimately move at once (~2 A steady plus four inrush spikes). It still protects the board: a 4S LiFePO₄ pack delivers tens of amps into a fault without noticing.

Commissioning

The board comes up once; the doors are commissioned one at a time with the other three motors unplugged. Steps 1–5 happen with all motors disconnected.

  1. Set the buck. U4 on the pack, nothing on its output, meter on OUT+/OUT−, trim to 5.00 V. Power down.
  2. Set and label the INA219 addresses. Bridge the A1/A0 jumpers per the address table before soldering the modules in, and mark each module with its door number.
  3. Bring up U1 alone. Flash door_lock_b.yaml over USB-C, then power it from U4 and confirm it joins Wi-Fi and Home Assistant.
  4. Confirm I²C. The boot log must print four lines: Found i2c device at address 0x40, 0x41, 0x44, 0x45. A missing address is a jumper problem; solve it before going further.
  5. Check each sense path. With motors unplugged but the 12 V branches live, every door's supply-side reading should behave: the shared supply voltage shows pack voltage, and each Door n motor current reads a few milliamps. A door stuck at a dead flat 0.000 A has a bridged shunt — measure 0.1 Ω across that module's VIN+/VIN− with power off.
  6. Per door, in turn — connect only that door's motor, then run variant A's sequence with that door's entities: verify direction with Door n jog unlock (swap the motor leads at U2n if inverted), measure free-running and stall currents, set the six Door n thresholds, measure the stroke and set min/max travel, and test the jam path with something soft.
  7. All together. Reconnect everything and command all four doors at once (this is what your future "close all" does). Watch supply voltage sag and confirm no door false-jams from the shared-rail dip. If one does, its stall threshold is too tight.

Setting the thresholds

Same six knobs as variant A, but per door — 24 number entities in all, each stored in flash. Doors with different actuators, stroke lengths, or friction will end up with different values; that is the point. The variant A guidance applies verbatim to each door:

If a door's free-running current is close to its stall current

Same escape hatch as variant A, per door: fit that door's SW-L/SW-U from Figure B2, turn on its Use position switches entity, and let the switches call end-of-travel while current detection stays as the jam guard. The other doors are unaffected.

What Home Assistant gets

Everything from variant A, four times over, prefixed Door 1 … Door 4 — plus one shared supply voltage sensor (all four INA219s sit on the same rail, so it is read from door 1's). Per door: the lock entity, motor current, last-move peak/duration, fault, last result, stop / clear-fault / jog buttons, the position-switch toggle, and six thresholds.

The single on-board LED is an aggregate: red = any door's fault latched · white = any door moving · green flash = a move just finished · off = all quiet.

One automation for all four doors

The fault event carries a door field, so one hook covers everything:

automation:
  - alias: Any door lock fault
    trigger:
      - platform: event
        event_type: esphome.door_lock_fault
    action:
      - service: notify.mobile_app_phone
        data:
          title: "{{ trigger.event.data.door }}: {{ trigger.event.data.reason }}"
          message: >-
            While {{ trigger.event.data.direction }} —
            {{ trigger.event.data.peak_current }} A after
            {{ trigger.event.data.travel_ms }} ms

"Close all" is just four service calls

The doors never wait on each other, so a close-all (or open-all) is a plain Home Assistant script — no firmware support needed:

script:
  close_all_doors:
    sequence:
      - service: lock.lock
        target:
          entity_id:
            - lock.door_locks_door_1
            - lock.door_locks_door_2
            - lock.door_locks_door_3
            - lock.door_locks_door_4

Firmware notes

The config lives in door_lock_b.yaml; copy secrets.yaml.example to secrets.yaml and fill it in first. All of variant A's firmware decisions carry over unchanged (no PWM, coast between moves, internal 20 Hz current sampling, per-move watchdog, time-based back-off). What is specific to B:

  • One copy of the logic. The whole per-door state machine lives in packages/door.yaml and is instantiated four times with per-door pins and addresses. Fix a bug once, all four doors get it.
  • Doors share nothing at runtime. Each has its own globals, scripts, thresholds, fault latch and 500 ms watchdog. A jam on door 2 cannot stall or delay a move on door 3 — including the watchdog forcing one bridge off while another is mid-travel.
  • The I²C bus is the only shared sensor path. Four INA219s at 50 ms each is a light load at 400 kHz; the state machines each run off their own internal fast sensor.
  • The LED is advisory. It aggregates four doors into one pixel; the per-door truth is always the lock entity, the fault sensor and last result.
